# 电商运营闭环设计

## 目标

把 B/4D 从“需求台账演示”提升为可操作的 PC 运营后台：保留现有商户、商品、订单、退款、结算页面，并新增一个贯通这些模块的业务工作台。运营人员可以推进真实的 Mock 状态、看到下一步、异常原因和完整审计记录。

## 方案比较

1. 逐个补齐 17 个领域：覆盖面大，但会产生大量浅功能，短期仍无法形成完整业务体验。
2. 重写后台：可以统一架构，但会丢弃已经成熟的商品、订单、商户和资金代码，风险与返工过高。
3. 纵向贯通一条核心闭环：复用现有页面，用一个小型状态机和运营工作台串联商户准入、商品上架、订单支付、履约、结算，并提供退款/对账分支。

采用方案 3。它能以最少新增代码产生最高的可感知业务价值，并为后续领域逐条纵向扩展提供模板。

## 产品结构

- 主导航以业务模块为主；“93 条需求追踪”降为独立辅助入口，不占据首要位置。
- 首页移除 AI 工作流监督内容，展示经营数据、待办与核心业务入口。
- 新增“电商运营工作台”，展示业务案例、当前阶段、资金状态、风险和下一步动作。
- 案例详情展示六阶段时间线、关键金额、关联主体、失败原因和审计日志。

## 状态与动作

主链路：

`待商户审核 → 待商品上架 → 待支付 → 待履约 → 待结算 → 已完成`

异常分支：

- 待支付及以后可进入退款申请；退款确认后进入已退款。
- 结算发生金额差异时进入待对账；差异处理后回到待结算。
- 每个动作必须满足来源状态，重复幂等键返回原结果，不允许跳步。

## 数据边界

- 继续使用本地 Mock 与 `localStorage`，不伪装真实后端。
- 金额统一使用整数分；比例统一使用整数基点。
- 每次状态变化写入操作人、动作、前后状态、时间和说明。
- 提供“恢复演示数据”操作，方便手工重复验收。

## 组件边界

- `domain/commerceWorkflow.ts`：状态、动作及案例类型。
- `services/commerceWorkflowService.ts`：状态机、持久化、幂等和审计。
- `pages/CommerceWorkbenchPage.tsx`：列表、详情、下一步动作与异常分支。
- `pages/DashboardPage.tsx`：只消费业务汇总，不包含 Harness/Agent 运行状态。
- `layouts/AdminLayout.tsx` 与 `App.tsx`：注册业务入口，并把需求追踪放到辅助区。

## 验收

- 新案例能按六阶段完整推进，不能跳步。
- 重复动作不重复写审计记录。
- 退款和对账分支受到状态约束，且能在 UI 中执行。
- 刷新页面后状态仍保留；恢复演示数据后回到初始状态。
- 工作台能跳转现有商户、商品、订单、退款和结算页面。
- 单元测试、类型检查、生产构建和浏览器关键流程全部通过。

## 非目标

- 本轮不实现真实支付、外部清结算、短信或第三方审核。
- 本轮不把 17 个领域全部做成独立生产系统。
- 本轮不新增 Harness、通用规则引擎、事件总线或后端服务。

## 自动批准依据

用户已授权后续不再提问并始终采用推荐路径。本设计按该授权直接进入实现；A/master 保持冻结，B/4D 承担产品化演进。
